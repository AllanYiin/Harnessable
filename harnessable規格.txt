# 規格整理 v 1.2.2

以下規格將 `harnessable` 定義為一套 **通用 Harness Engineering 框架**。核心目標是讓 chat、agent、multi-agent 都能共用同一套控制架構，並且讓未來新增、修改、停用 Harness 規則、fallback 策略、工具管控、記憶管控、人工審核與回歸測試時，不需要大幅重構主程式。

本文件採以下合理假設：

1. `harnessable` 是一個可被應用程式引入的 package，預設以 SDK / CLI / 本機管理介面三種方式使用。
2. 技術選項不強綁特定模型供應商、資料庫、前端框架、agent 框架或雲端平台。
3. 為了讓 Codex / Claude Code 可以直接開始開發，檔案清單以 Python package 結構作為落地基準；若未來改用 TypeScript、Go 或其他語言，模組邊界與契約仍保持一致。
4. `harnessable` 不是單純 guardrail，也不是單純 prompt 管理器，而是 LLM Runtime Control Plane：管理事件、規則、能力、決策、狀態、fallback、審核、觀測與回放測試。
5. 所有 LLM 產生式輸出，包括規則建議、fallback 說明、審核摘要、測試報告摘要，一律支援 Streaming。
6. 所有專案資料必須能以「專案」形式開啟、保存、關閉後繼續編輯。
7. 所有匯入檔案，例如規則檔、測試案例、能力定義、回放紀錄，必須先提供預覽與驗證結果，使用者確認後才寫入專案。
8. 所有圖形縮放，包括流程圖、執行紀錄圖、規則關聯圖，必須維持原始寬高比。

# 一、技術規格文件（Technical Spec）

## 1. 背景

目前許多 chat、agent、multi-agent 系統的控制邏輯散落在 prompt、工具包裝函式、流程控制器、例外處理、UI handler、測試程式與部署腳本中。這會造成幾個問題：

第一，新增一條規則時，可能需要同時修改 prompt、tool wrapper、agent loop、輸出檢查與測試流程。第二，chat 與 agent 常常各自有一套安全與品質控制，導致規則重複、行為不一致。第三，fallback 常被寫成局部 `try/except`，缺乏一致的失敗分類、降階策略、狀態保存與觀測。第四，multi-agent 增加 handoff、共享狀態、代理間訊息、分支合併與衝突仲裁後，既有 guardrail 架構難以擴充。

`harnessable` 的目的，是把這些控制面抽象成一套可組合、可測試、可回放、可版本化的 Harness Kernel。

## 2. 目標

`harnessable` 需要達成以下目標：

1. 提供一套通用事件模型，讓 chat、agent、multi-agent 都能轉成相同的 `HarnessEvent`。
2. 提供規則引擎，讓規則可透過設定或外掛新增，不需重寫 runtime。
3. 提供決策語意，讓所有規則輸出標準化 `HarnessDecision`，例如允許、註記、轉換、重試、轉派、要求審核、阻擋、終止、回復。
4. 提供能力閘道，統一治理模型、工具、記憶、資源、代理與外部副作用。
5. 提供 fallback / resilience plane，以 `FailureSignal`、`FallbackPolicy`、`FallbackGraph`、`DegradationBudget` 管理優雅降階。
6. 提供專案保存與續編能力，讓規則、能力、測試、執行紀錄、回放結果都可被保存、開啟、版本化。
7. 提供觀測與審計能力，完整記錄事件、規則命中、決策、工具呼叫、fallback、審核與回放結果。
8. 提供評測與回放能力，讓規則變更可先用歷史案例或測試案例驗證。
9. 提供 CLI 與本機管理介面，讓使用者可建立專案、匯入規則、預覽檔案、執行測試、檢視紀錄與調整策略。
10. 支援未來新增 runtime adapter，例如 voice agent、browser agent、batch workflow、server-side automation，而不改 Harness Kernel。

## 3. 範圍

本版 `harnessable` 包含：

1. Harness Kernel。
2. Runtime Adapter 介面。
3. Chat / Agent / Multi-agent adapter 的基準實作。
4. Event Bus。
5. Rule Registry / Rule Engine。
6. Condition Engine。
7. Detector Plugin Interface。
8. Decision Aggregator。
9. Execution Governor。
10. Capability Registry。
11. Model / Tool / Memory / Resource / Agent / External Action Gateways。
12. Fallback / Resilience Manager。
13. Approval / Interruption Manager。
14. State Store / Artifact Store / Project Store。
15. Observability / Audit。
16. Evaluation / Replay Engine。
17. CLI。
18. 本機管理介面。
19. 內建規則範例。
20. 內建 fallback policy 範例。
21. 範例專案與整合測試。

## 4. 不做什麼

本版不做以下事項：

1. 不綁定任何單一 LLM 供應商。
2. 不綁定任何單一 agent framework。
3. 不提供託管雲服務。
4. 不提供完整企業 IAM 系統。
5. 不自行實作大型向量搜尋引擎。
6. 不保證所有政策判斷自動正確；inferential detector 必須保留信心分數與回放測試。
7. 不讓 fallback 繞過安全、權限、隱私、審計與人工審核。
8. 不把多代理協作寫死成單一 supervisor pattern；只提供通用事件與能力邊界。
9. 不把 UI 做成完整多租戶 SaaS；本版以本機或內部管理介面為主。
10. 不將 LLM 產生的規則自動上線；只能建議、預覽、測試與人工啟用。

## 5. 技術可行性分析

### 5.1 可行性

`harnessable` 可行，原因是 chat、agent、multi-agent 的共同本質都可以被抽象成：

```text
Actor 發起行為
Capability 被使用
Artifact 被讀寫
Event 被觸發
Decision 被套用
State 被更新
Trace 被記錄
```

只要所有 runtime 透過 adapter 轉成標準事件，Kernel 就不需要知道原生框架細節。

### 5.2 主要限制

1. 不同模型供應商的 tool calling、streaming、structured output 支援程度不同，需要透過 Capability Profile 宣告能力差異。
2. Inferential detector 可能有誤判，需要 shadow mode、信心分數、人工審核與回放測試。
3. 外部副作用，例如寄信、付款、刪除、部署，不能用一般 retry 邏輯處理，必須有 idempotency key、side-effect state 與 approval。
4. Multi-agent 的 shared state 與 handoff 可能出現競態，需要 ownership、lock、merge policy 與 conflict resolution。
5. Fallback 可能造成成本與延遲失控，因此必須有 Degradation Budget。
6. 規則越多，衝突越多，因此需要 Decision Aggregator 與明確優先級。

### 5.3 替代方案

| 替代方案                              | 優點        | 缺點                                       | 結論                            |
| --------------------------------- | --------- | ---------------------------------------- | ----------------------------- |
| 每個 chat / agent 各自實作 guardrail    | 初期快速      | 規則重複、難以維護、fallback 分散                    | 不採用                           |
| 只用 prompt 寫規則                     | 成本低       | 不可測、不可觀測、不可保證工具行為                        | 只能作為 Instruction Harness 的一部分 |
| 只包裝工具函式                           | 對 tool 有效 | 無法管理 model、context、memory、handoff、output | 不足                            |
| 使用單一 agent framework 的 middleware | 開發快       | 綁定框架，難以跨 runtime                         | 可作為 adapter，但不作為核心            |
| 建立 Harness Kernel                 | 初期設計較重    | 可擴充、可測、可回放、可治理                           | 採用                            |

## 6. Persona

### 6.1 AI Platform Engineer

負責把 `harnessable` 接到內部 chat、agent、multi-agent 系統。關注模組邊界、穩定性、可測性、observability、fallback、權限與維護成本。

### 6.2 AI Product Manager

負責定義哪些規則要啟用、哪些情境需要人工審核、哪些任務可以降階、哪些輸出必須提示限制。關注使用者體驗、風險、上線節奏與指標。

### 6.3 AI Safety / Governance Reviewer

負責審查規則、審計紀錄、fallback 是否繞過安全控制、工具是否有越權風險。關注 audit trail、rule version、approval、replay report。

### 6.4 Agent Builder

負責建立 chat、agent、multi-agent 應用。希望用同一套方式管理工具、記憶、輸出格式、fallback、審核與測試，不想每個 agent 重寫控制邏輯。

### 6.5 QA / Evaluation Engineer

負責建立 golden cases、failure injection、regression test、shadow mode test。關注規則變更是否造成過度阻擋、錯誤放行或品質下降。

## 7. 系統總覽

`harnessable` 採用五層架構：

```text
Application Layer
Runtime Adapter Layer
Harness Kernel Layer
Gateway Layer
External Systems Layer
```

核心原則：

1. Runtime 不直接呼叫模型、工具、記憶、代理或外部副作用。
2. Runtime 必須先產生 `HarnessEvent`。
3. Rule Engine 只輸出 `HarnessDecision`，不直接改流程。
4. Execution Governor 是唯一能改變 run control flow 的模組。
5. 所有能力都經過 Capability Gateway。
6. 所有 fallback 都經過 Fallback Manager。
7. 所有執行都寫入 trace 與 audit log。
8. 所有規則與 fallback policy 都可版本化、回放與測試。

## 10. 核心架構

### 10.1 核心公式

```text
harnessable =
  Event Model
  + Rule Engine
  + Decision Algebra
  + Capability Gateway
  + State / Trace / Replay
  + Resilience / Fallback Plane
  + Approval / Interruption
  + Project Persistence
```

### 10.2 核心抽象

| 抽象                | 定義                                                                      |
| ----------------- | ----------------------------------------------------------------------- |
| `Actor`           | 執行行為者，例如 user、assistant、agent、tool、human reviewer                       |
| `Capability`      | 可被使用的能力，例如 model、tool、memory、resource、agent、external action             |
| `Artifact`        | 被讀寫的資料，例如 message、context packet、tool result、file、trace、approval record |
| `HarnessEvent`    | runtime 發生的標準事件                                                         |
| `HarnessRule`     | 在某些事件上生效的規則                                                             |
| `DetectionResult` | 偵測器對事件的判斷                                                               |
| `HarnessDecision` | 規則產生的標準決策                                                               |
| `FailureSignal`   | 標準化失敗訊號                                                                 |
| `FallbackPolicy`  | 失敗後的降階策略                                                                |
| `FallbackGraph`   | fallback 節點與路徑                                                          |
| `RunState`        | 一次執行的狀態                                                                 |
| `Project`         | 規則、能力、測試、紀錄與設定的保存單位                                                     |

## 11. 使用流程

### 11.1 建立專案流程

```text
harnessable init
  -> 建立 project manifest
  -> 建立 rules / capabilities / fallback / evals 目錄
  -> 建立預設 rule profile
  -> 建立 persistence adapter
  -> 執行 health check
```

### 11.2 接入 chat 流程

```text
Application receives user input
  -> ChatRuntimeAdapter emits USER_INPUT_RECEIVED
  -> Harness Kernel evaluates input rules
  -> Context assembly
  -> ModelGateway emits MODEL_CALL_REQUESTED
  -> Rule Engine evaluates model rules
  -> ModelGateway streams model output
  -> Output rules validate final answer
  -> Trace and audit logs written
```

### 11.3 接入 agent 流程

```text
Agent loop requests tool call
  -> AgentRuntimeAdapter emits TOOL_CALL_REQUESTED
  -> ToolGateway checks capability profile
  -> Rule Engine checks permissions / arguments / risk
  -> Approval Manager interrupts if needed
  -> Tool executes only after allowed
  -> Tool result emits TOOL_CALL_COMPLETED
  -> Tool result sanitizer and injection detector run
  -> Agent continues or fallback triggers
```

### 11.4 接入 multi-agent 流程

```text
Coordinator proposes handoff
  -> MultiAgentRuntimeAdapter emits AGENT_HANDOFF_REQUESTED
  -> AgentGateway checks role contract and context visibility
  -> Handoff packet is filtered
  -> Specialist agent runs through same Kernel
  -> Shared state write goes through Gateway
  -> Aggregation runs validation
  -> Final output passes output rules
```

### 11.5 Fallback 流程

```text
Gateway failure
  -> FailureClassifier creates FailureSignal
  -> FallbackPolicyRegistry matches policies
  -> FallbackManager builds FallbackPlan
  -> DegradationBudget checked
  -> ExecutionGovernor applies retry / route / transform / degrade / partial / approval / fail-safe
  -> Every fallback action emits new HarnessEvent
  -> All new events still pass rules
```

DRAFT -> SHADOW -> ACTIVE -> DISABLED -> DEPRECATED -> ARCHIVED

## 13. G3M

### Goal

1. 讓 chat、agent、multi-agent 共用同一套 Harness Kernel。
2. 讓新增規則與 fallback policy 大多可透過設定完成，不改核心程式。
3. 讓所有外部能力使用前後都有一致事件、規則、決策、觀測與回放。
4. 讓 fallback 優雅降階，不降低安全、權限、隱私、審計與誠實性。
5. 讓專案能保存、打開、續編、測試與交付。

### Gaps

1. 不同 runtime 的 native event 不一致，需要 adapter。
2. 不同工具與模型的能力不一致，需要 Capability Profile。
3. 規則可能衝突，需要 Decision Aggregator。
4. Fallback 可能繞過規則，需要保證 fallback action 仍走 HarnessEvent。
5. LLM-based detector 可能誤判，需要 shadow mode、confidence、eval、replay。
6. 副作用操作可能出現未知狀態，需要 idempotency、approval、manual check。
7. 多代理交接可能造成上下文外洩或職責混亂，需要 Role Contract 與 Agent Gateway。

### Metrics

| 指標                           | 目標                    |
| ---------------------------- | --------------------- |
| 新增 declarative rule 不改核心程式比例 | ≥ 80%                 |
| 規則回歸測試覆蓋率                    | ≥ 90% P0 規則           |
| Fallback 成功率                 | ≥ 85% 可恢復失敗           |
| Fallback 繞過安全規則次數            | 0                     |
| Side-effect unknown 被宣稱成功次數  | 0                     |
| Project reopen 後可續編成功率       | 100% P0 測試            |
| Rule shadow mode 可觀測率        | 100% shadow rule      |
| Trace event coverage         | ≥ 95% gateway actions |
| Import preview 覆蓋率           | 100% 上傳 / 匯入入口        |
| SVG / trace graph 縮放比例錯誤     | 0                     |

## 15. 資料模型 / Persistence Schema

### 15.1 設計原則

1. `harnessable` 透過 Persistence Adapter 儲存資料，不強綁特定資料庫。
2. 本機專案可用檔案型儲存；服務化部署可映射到關聯式資料庫或文件型儲存。
3. Run event、decision、audit log 預設 append-only。
4. 規則、能力、fallback policy、eval case 採版本化。
5. 敏感 payload 預設儲存 artifact reference，不直接寫入 trace。
6. 匯入檔案必須先 preview，再 apply。

### 15.2 Entity Schema

#### `projects`

| 欄位               | 類型                | 說明                                              |
| ---------------- | ----------------- | ----------------------------------------------- |
| `id`             | string            | 專案 ID                                           |
| `name`           | string            | 專案名稱                                            |
| `version`        | string            | 專案格式版本                                          |
| `status`         | enum              | NEW / OPEN / DIRTY / SAVED / ARCHIVED / DELETED |
| `policy_profile` | string            | 預設政策設定                                          |
| `created_at`     | datetime          | 建立時間                                            |
| `updated_at`     | datetime          | 更新時間                                            |
| `archived_at`    | datetime nullable | 封存時間                                            |

#### `rules`

| 欄位               | 類型       | 說明                                                         |
| ---------------- | -------- | ---------------------------------------------------------- |
| `id`             | string   | 規則 ID                                                      |
| `project_id`     | string   | 所屬專案                                                       |
| `version`        | string   | 規則版本                                                       |
| `name`           | string   | 規則名稱                                                       |

## 17. Rule Model

### 17.1 `HarnessRule`

```yaml
id: security.prompt_injection.tool_result.v1
name: Detect prompt injection in tool observations
version: "1.0.0"
enabled: true

applies_to:
  runtimes:
    - chat
    - agent
    - multi_agent
  actors:
    - "*"
  capability_types:
    - TOOL
    - RESOURCE
  event_types:
    - TOOL_CALL_COMPLETED
    - RESOURCE_READ_COMPLETED

hook:
  point: after_tool_call
  priority: 200
  mode: blocking

condition:
  expression: |
    event.payload.content_classification.source_trust != "trusted"
    OR event.risk.level in ["medium", "high"]

detector:
  type: inferential
  implementation: prompt_injection_classifier_v3
  timeout_ms: 1500
  streaming: true

action:
  when_detected:
    type: TRANSFORM
    transform:
      strategy: sanitize_and_summarize
  when_uncertain:
    type: REQUIRE_APPROVAL
  when_detector_failed:
    type: BLOCK

severity: high

telemetry:
  emit_trace_event: true
  emit_metric: true
  audit_payload: metadata_only

testing:
  golden_set: evals/security/prompt_injection_tool_result.yaml
  shadow_mode_supported: true

ownership:
  owner: ai-platform
  created_at: "2026-05-23"
```

### 17.2 Rule Execution

```text
1. Event Bus receives HarnessEvent
2. Rule Registry matches candidate rules
3. Condition Engine filters rules
4. Detector evaluates event
5. Action maps DetectionResult to HarnessDecision
6. Decision Aggregator merges decisions
7. Execution Governor applies final decision
8. Trace and audit records are written
```

### 20.4 Fallback Policy

```yaml
id: resilience.tool.search.v1
name: Search tool fallback
enabled: true
version: "1.0.0"

applies_to:
  runtimes:
    - chat
    - agent
    - multi_agent
  event_types:
    - TOOL_CALL_FAILED
  capability_types:
    - TOOL
  compatibility_class:
    - web_search

triggers:
  any_of:
    - failure.category in ["TIMEOUT", "RATE_LIMIT", "PROVIDER_5XX"]
    - validator.result_empty == true

constraints:
  max_total_attempts: 4
  max_fallback_depth: 3
  max_added_latency_ms: 15000
  max_added_cost_usd: 0.10
  never_degrade:
    - safety_policy
    - privacy_policy
    - tool_permission
    - tenant_isolation

fallback_graph:
  - id: retry_primary
    level: L1_LOCAL_RECOVERY
    when: failure.recoverability == "TRANSIENT"
    action:
      type: RETRY
      target: same_capability
      max_attempts: 2
      backoff:
        strategy: exponential
        initial_delay_ms: 500
        max_delay_ms: 5000
        jitter: true
    success_criteria:
      - tool_result.received == true
      - guardrails.passed == true

  - id: alternate_search_provider
    level: L2_EQUIVALENT_SUBSTITUTION
    action:
      type: ROUTE
      selector:
        capability_type: TOOL
        compatibility_class: web_search
        side_effect: false
        same_or_stricter_data_policy: true

  - id: internal_kb
    level: L3_REDUCED_CAPABILITY
    action:
      type: ROUTE
      target: tool.internal_knowledge_search
    disclosure:
      required: true
      template: "外部搜尋暫不可用，以下僅根據內部資料回答。"

  - id: partial_no_external_verification
    level: L4_PARTIAL_COMPLETION
    action:
      type: RETURN_PARTIAL
      disclosure:
        required: true

  - id: fail_safe
    level: L6_FAIL_SAFE
    action:
      type: FAIL_SAFE
      user_message_template: "目前無法可靠完成這個請求，因此不提供可能誤導的結果。"
```

### 20.5 Side-effect Handling

外部副作用必須具備：

```text
idempotency_key
side_effect_status
confirmation check
rollback or compensation plan
manual review path
audit log
```

狀態：

```text
NOT_STARTED -> STARTED -> CONFIRMED
             ├────────> FAILED
             ├────────> UNKNOWN
             └────────> ROLLED_BACK
```

若狀態為 `UNKNOWN`，不得自動重試，也不得對使用者宣稱成功。

## 22. 非功能需求

### 22.1 效能

1. Rule matching P95 應低於 20ms，不含 detector 外部呼叫。
2. Computational detector P95 應低於 50ms。
3. Inferential detector 必須支援 timeout 與 fallback。
4. Streaming model output 不得因 output validation 完全阻塞；可採 streaming buffer 與 final validation 組合。
5. Fallback 不得無限重試，必須受 Degradation Budget 控制。

### 22.2 安全

1. Tool / action gateway 必須預設 deny-by-default。
2. Prompt injection 風險資料不得直接進入下一輪模型上下文，須先 sanitize、summarize 或 block。
3. Secret、token、credential 預設不得寫入 trace。
4. Artifact payload 預設使用 reference，不直接展開。
5. 匯入規則檔必須驗證，禁止匯入可執行任意程式的設定。
6. Plugin detector 必須明確註冊與授權。

### 22.3 隱私

1. PII 讀寫需經 rule 判斷。
2. Memory write 必須支援 consent policy。
3. Artifact 支援 redaction 與 purge。
4. Trace 預設 metadata-only。
5. Tenant / project boundary 不可被 fallback 降階。

### 22.4 可用性

1. Project 可保存、關閉、重新開啟與續編。
2. Run interrupted 後可 resume。
3. Approval pending 不應遺失上下文。
4. Fallback graph 可視覺化。
5. 匯入檔案提供預覽、錯誤定位與修正建議。

### 22.5 可維護性

1. Kernel、Gateway、Adapter、Plugin 邊界清楚。
2. Rule 不直接控制流程，只產生 Decision。
3. Gateway 不寫死 policy，只產生事件並執行 Governor 指令。
4. 新增 runtime 只需新增 adapter。
5. 新增 capability 只需新增 profile 與 gateway binding。
6. 新增 detector 只需實作 detector interface。
7. 新增 fallback 只需新增 policy 或 fallback node plugin。

### 22.6 可觀測性

所有以下項目必須 trace：

```text
event
rule match
condition result
detector result
decision
governor command
gateway call
fallback step
approval
artifact creation
replay result
```

## 24. Edge / Abuse Cases

| 情境                              | 處理行為                                      | 使用者或操作提示                |
| ------------------------------- | ----------------------------------------- | ----------------------- |
| 匯入惡意規則檔                         | 阻擋匯入，顯示危險欄位與位置                            | 「此規則包含不允許的動作，未套用。」      |
| 規則互相衝突                          | Decision Aggregator 依優先級處理；無法合併則 block    | 「規則衝突，請先修正後再啟用。」        |
| Tool result 包含 prompt injection | sanitize 或 block，不直接進入模型上下文               | 「外部內容包含可疑指令，已隔離。」       |
| 使用者要求繞過審核                       | 拒絕，保留 audit                               | 「此操作需要審核，不能略過。」         |
| Fallback target 權限較寬            | 禁止 route                                  | 「備援能力不符合權限邊界，已停止。」      |
| Side-effect 狀態未知                | 不自動重試，不宣稱成功，要求確認                          | 「無法確認是否完成，為避免重複執行，已暫停。」 |
| Multi-agent handoff loop        | 停止 handoff，交由 supervisor 或 fail-safe      | 「工作交接重複，已改由主控流程收斂。」     |
| Shared state 同時寫入               | lock / merge policy / conflict event      | 「有多個修改衝突，請檢查後套用。」       |
| 記憶寫入含敏感資料                       | 需 consent 或 redact                        | 「此內容可能包含敏感資訊，未直接保存。」    |
| Output schema invalid           | retry repair，超過次數 block 或 partial         | 「輸出格式未通過檢查，已重新產生。」      |
| Replay 結果與線上不同                  | 標記 nondeterministic，要求人工檢查                | 「回放結果與原始執行不一致。」         |
| 檔案太大無法預覽                        | 顯示摘要與大小限制，要求切分                            | 「檔案過大，請切分後再匯入。」         |
| SVG 或 trace graph 縮放            | 強制 aspect ratio lock                      | 不顯示錯誤，只維持比例             |
| LLM detector timeout            | 依 fallback policy 轉 computational 或 block | 「語意檢查逾時，已採安全處理。」        |
| 使用者重複提交                         | idempotency key 去重                        | 「此操作已收到，避免重複執行。」        |

## 25. 驗收條件

### 25.1 核心架構驗收

1. 新增一條 YAML rule，不修改 Kernel 程式碼，即可在 `before_tool_call` 生效。
2. 同一條 rule 可同時套用 chat、agent、multi-agent，只需 adapter 產生對應事件。
3. Rule Engine 對相同事件與相同規則集的 decision 結果可重現。
4. Decision Aggregator 可正確處理 `BLOCK > RETRY > TRANSFORM > ALLOW`。
5. Execution Governor 是唯一能執行 retry、route、approval、rollback 的模組。
6. 所有 Gateway action 都會產生 trace event。
7. fallback action 產生的新行為仍會重新進入 HarnessEvent 流程。

### 25.2 專案保存驗收

1. 建立專案後可保存到磁碟。
2. 關閉後重新開啟，規則、能力、fallback policy、測試案例、執行紀錄仍存在。
3. 修改 rule 後 project 進入 DIRTY；保存後進入 SAVED。
4. Import 前必須有 preview；未 preview 不可 apply。
5. Upload / import 的規則、能力、測試案例都可預覽、驗證與取消。

### 25.3 Fallback 驗收

1. 模型 timeout 後，可依 policy retry，失敗後 route 到相容模型。
2. Tool rate limit 後，可 route 到相容 tool；若 fallback tool 權限較寬，必須阻擋。
3. Side-effect tool 狀態 unknown 時，不可自動重試，不可宣稱成功。
4. Fallback 超過 Degradation Budget 時，必須 fail-safe。
5. Reduced capability 或 partial completion 必須產生 user-visible disclosure。

### 25.4 Streaming 驗收

1. ModelGateway 的 LLM 輸出必須支援 streaming。
2. LLM-based detector 若產生說明、摘要或審核建議，必須 streaming。
3. Console UI 顯示 LLM 產生內容時，需逐步顯示，不等待完整完成。
4. Streaming 過程中若 rule block，需停止後續輸出並顯示安全訊息。

### 25.5 UI 驗收

1. 預設為淺色模式。
2. 匯入檔案時先顯示 preview、validation errors、warnings、apply / cancel。
3. Fallback graph 與 trace graph 可縮放，縮放時保持原始寬高比。
4. Run trace 可以看到 event、decision、fallback step、approval。
5. Rule 頁面可 create / update / disable / shadow / archive。

# 二、非技術規格文件（白話版）

## 1. 這是什麼

`harnessable` 是一套管理中心，用來規劃「自動助理」該怎麼接收訊息、使用工具、遇到失敗怎麼處理、什麼情況需要人工確認、最後回答前要檢查什麼。

它的重點不是讓自動助理變得更會說話，而是讓自動助理做事時更可控、更安全、更容易調整。

你可以把它想成：

```text
一套自動助理的交通規則、檢查站、備援路線與紀錄本。
```

## 2. 它能做什麼

`harnessable` 可以做到：

1. 管理規則：例如哪些內容不能回答、哪些工具不能亂用、哪些情況要先確認。
2. 管理工具：例如搜尋、讀檔、寫檔、寄信、查資料、交給其他自動工作者。
3. 管理失敗時的處理方式：例如重試、改用備用工具、只完成部分內容、請人確認、安全停止。
4. 管理多個自動工作者：例如研究者、整理者、檢查者之間怎麼交接。
5. 管理專案：規則、工具、測試、紀錄都可以保存在同一個專案中，之後再打開繼續調整。
6. 管理匯入檔案：匯入規則或測試資料前，會先顯示預覽與問題，不會直接套用。
7. 管理紀錄：每次自動助理做了什麼、哪條規則生效、哪一步失敗、如何降階，都能查到。
8. 管理測試：修改規則後，可以用舊案例重跑，確認沒有造成新的問題。

## 3. 誰會使用

### 產品負責人

用來決定哪些行為可以自動完成，哪些行為需要人工確認，哪些情況要明確提醒使用者。

### 風險審查人員

用來查看規則是否合理、紀錄是否完整、失敗時有沒有不安全地繞路。

### 自動助理建置者

用來接上不同對話功能、工具功能、多人協作流程，並共用同一套規則。

### 測試人員

用來建立測試案例，確認新規則不會誤擋正常任務，也不會放過危險任務。

## 4. 基本使用方式

第一步，建立一個專案。

你會得到一個專案工作區，裡面可以放規則、工具清單、降階方案、測試案例與執行紀錄。

第二步，加入規則。

例如：

```text
如果自動助理想寄信，必須先確認收件人與內容。
如果外部內容看起來像在命令自動助理改變行為，要先隔離。
如果回答需要最新資料，但目前不能確認，就要提醒使用者。
```

第三步，加入工具。

例如搜尋、讀文件、產生草稿、寄信、交給另一個自動工作者。

第四步，設定失敗時怎麼辦。

例如：

```text
先重試一次。
再改用備用工具。
如果只能完成部分內容，就明確說明限制。
如果涉及寄信、付款、刪除，就不要自動重試，改為人工確認。
```

第五步，執行測試。

修改規則後，可以用既有案例重跑，確認新規則沒有破壞原本流程。

第六步，查看紀錄。

可以看到自動助理每一步做了什麼、哪條規則生效、是否有降階、是否有人審核。

## 5. 專案可以保存與續編

`harnessable` 的所有設定都保存在專案裡。

你可以：

1. 建立專案。
2. 修改規則。
3. 匯入測試資料。
4. 執行測試。
5. 關閉專案。
6. 下次重新打開後繼續調整。

系統會顯示專案是否已保存。如果你修改了內容但還沒保存，畫面會提示。

## 6. 匯入檔案會先預覽

當你匯入規則、工具設定或測試案例時，不會立刻套用。

畫面會先顯示：

1. 哪些內容有效。
2. 哪些內容有警告。
3. 哪些內容不能套用。
4. 會新增或修改哪些項目。

你確認後才會套用。

如果檔案太大，畫面會先顯示摘要，並提示需要切分。

## 7. 失敗時的優雅降階

`harnessable` 不會把失敗都當成同一種錯誤。它會先判斷失敗類型，再決定怎麼處理。

常見處理方式：

| 情況          | 處理方式            |
| ----------- | --------------- |
| 暫時連不上       | 重試              |
| 原本工具不可用     | 改用相同用途的備用工具     |
| 取得資料不完整     | 先完成能完成的部分，並說明限制 |
| 需要最新資料但無法確認 | 不做肯定說法          |
| 需要寄信、付款、刪除  | 不自動重試，先請人確認     |
| 風險太高        | 停止並提示原因         |

重要原則：

```text
可以降低完整度，但不能降低安全性。
可以改用備援方式，但不能繞過確認。
可以先給部分結果，但不能假裝結果完整。
```

## 8. 使用者會看到什麼

畫面會分成幾個主要區域：

1. 左邊是功能選單。
2. 上方是目前專案與操作按鈕。
3. 中間顯示專案健康狀態、規則、工具與降階路線。
4. 右側或下方顯示執行紀錄與匯入預覽。
5. 有需要確認的操作會出現在審核區。

畫面預設是淺色，重要顏色如下：

| 顏色 | 代表意思              |
| -- | ----------------- |
| 藍色 | 主要操作，例如執行、套用、開始測試 |
| 綠色 | 通過、正常、已啟用         |
| 橘色 | 警告、降階、需要注意        |
| 紅色 | 阻擋、失敗、安全停止        |
| 灰色 | 說明、次要資訊           |

## 10. 常見提示語

| 情況       | 會看到的提示                    |
| -------- | ------------------------- |
| 匯入檔案有問題  | 「此檔案有 1 個項目不能套用，請查看原因。」   |
| 需要人工確認   | 「這個操作會影響外部對象，請先確認。」       |
| 只能完成部分內容 | 「我已完成可確認的部分，以下內容仍有限制。」    |
| 不能確認是否完成 | 「我無法確認這個操作是否成功，因此不會重複執行。」 |
| 外部資料不可用  | 「目前無法取得外部資料，以下僅根據現有內容整理。」 |
| 規則衝突     | 「有兩條規則互相衝突，請先修正後再啟用。」     |
| 測試失敗     | 「修改後有測試未通過，請查看失敗案例。」      |

## 11. 限制

1. 它不能保證自動助理永遠不犯錯。
2. 它不能取代人工審查，尤其是高風險操作。
3. 它不能把沒有取得的資料變成可靠答案。
4. 它不能在不確認成功的情況下宣稱操作完成。
5. 它不能讓備用方式繞過安全限制。
6. 如果規則寫得太模糊，測試結果也會不穩定。
7. 如果外部工具本身不可用，只能降階、部分完成或停止。

# 三、Codex / Claude Code 分階段開發計畫

此計畫依照「可交付、可測試、可回滾」切分。Codex instructions 採較 runbook 化的工作說明；Claude Code instructions 採較短、具體、結構化的說明。這種差異與上傳參考文件中的建議一致：Claude Code 適合短而清楚的結構，Codex 適合更像工作流程的操作指引。

---
